Two things have to hold of `/app` at the end: `/app/data/policy_rules.json` holds the rebuilt record the rest of this describes, and `/app/workflow/compile_policy.go` is a program whose behaviour is the one the governing decisions settle, so that a run of it produces the three artifacts `/app/docs/policy_contract.json` names. What follows is where those two come from and what has to be true of them.

A failed configuration migration stalled a firewall policy push. It truncated the authoritative rule base at `/app/data/policy_rules.json` and left the policy compiler at `/app/workflow/compile_policy.go` deciding what to install under draft rules the change advisory board later reversed. Nothing the compiler emits can be trusted until that rule base is rebuilt. A pre-migration snapshot and a journal of the changes the migration posted after it survive beside the truncated file under `/app/data`, alongside the object-group catalogue the rules address each other through. How the snapshot and the journal combine, which rule a change names, what a retraction does, what a later restoration brings back, and how a group whose members name other groups resolves to a set of prefixes are governance decisions, and the rule base is restored in place at `/app/data/policy_rules.json` where the truncated file sits, with both sides of every rule already resolved. Nothing the compiler decides means anything against the truncated file, so that rebuild is what the compiled policy is read from: whatever order you work in, the rule base that is there at the end is the one every graded run is handed.

The restored compiler at `/app/workflow/compile_policy.go` is a Go program built with the toolchain installed here. It is built and run under the execution terms the contract sets out, which say how it is compiled, what it may bring in, and which routes to another process are closed to it. Preserve its `--input` and `--output-dir` options and their defaults, and declare no other option; the firewall policy is always read from its fixed absolute path under `/app/data`, and `--input` selects the rule base only. `/app/docs/policy_contract.json` is the output contract: paths, schemas, required-field lists, container shapes, sort orders, and a note against each field saying what that field counts. What those notes leave open -- which is every rule that decides a value rather than names it -- is settled in `/app/incident/network_governance_log.md`, mostly routine change-advisory minutes, where the later dated decision governs. A run writes exactly the three artifacts the contract names -- `/app/output/summary.json`, `/app/output/compiled_policy.json` and `/app/output/exception_queue.jsonl` where the option is left at its default, and those same three names in the directory `--output-dir` selects otherwise -- and anything an earlier run left in that directory is cleared rather than passed off as this run's output; the contents are what is cleared, since the run does not own the path it writes into, whichever path that is. When a run finishes, nothing outside that directory has been added to, changed or taken away by it -- scratch elsewhere is the run's own business while it lasts, and it goes when the run does. The contract states the scale a run is expected to handle.

These hold of the artifacts and of the program that produces them, and a run that misses any of them is not a correct one. Every value in them is derived from the operational inputs: correct against an alternate rule base, identical across reruns. The recovery sources and the rule documents are what this work is done from rather than things it writes, so the pre-migration snapshot, the configuration journal, the object groups, the firewall policy, the governance log and the output contract at `/app/docs/policy_contract.json` all come back byte for byte unchanged, and the frozen snapshot `/app/workflow/.compile_policy.original.go` is left exactly as it is.
